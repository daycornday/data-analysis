# "검증했다"를 등급으로 나누는 검사 키트

> 한 줄 요약: 버그 다섯 개를 심은 마트와 고친 마트에 같은 검사 11개를 돌리면, 둘 다 에러 없이 돌아가지만(V0) 버그 마트는 9개 검사에서 걸려 V0에 머물고, 고친 마트는 전부 통과해 문서 레벨 V2(일별 매출만 V3)를 받는다.

## 질문

분석 결과를 공유할 때 "검증했다"는 말은 사람마다 범위가 다르다. 쿼리가 돌아간 것, 내가 만든 숫자끼리 맞춘 것, 외부 기준과 전부 맞춘 것이 같은 단어로 묶이면 듣는 사람은 확인 범위를 과대평가한다. 이 프로젝트는 실무에서 자주 나는 마트 버그 다섯 가지를 일부러 심고, 어떤 검사가 각 버그를 잡는지, 그 검사가 검증 레벨(V0~V3) 중 어디에 해당하는지를 코드로 보여 준다.

## 결론

- 버그 마트도 빌드는 에러 없이 끝난다. "쿼리가 돌아갔다"(V0)만으로는 아무것도 걸러지지 않는다
- 조인 fan-out으로 주문 마트가 1,111행에서 2,192행으로 늘고 금액 합이 67,492,000에서 134,037,000으로 1.99배가 된다. 키 유일성, 행 수 보존, 합계 대조 세 검사가 모두 잡는다
- 채널 NULL 누락으로 9월 채널별 매출 합이 3,574,000(7.2%) 모자라고, 기간 경계 오류로 9/30 하루치 1,567,000(3.2%)이 빠진다. 키 유일성은 두 버그를 못 잡고 합계 대조, 경계 확인, 전수 대조가 잡는다
- 전환율은 정수 나눗셈으로 0이 되고, 분모를 전체 가입자 2,000명으로 잡아 정의상 모집단 1,822명과 어긋난다(실수 나눗셈으로 고쳐도 31.60%로, 맞는 값 34.69%보다 3.1%p 낮다)
- 같은 검사 11개에서 버그 마트는 2개, 고친 마트는 11개 통과한다. 고친 마트도 문서 레벨은 가장 낮은 마트를 따라 V2이고, 미검증 범위를 검증 카드에 남긴다

## 방법

1. **합성 원천 테이블** (`src/analysis_validation_kit/data.py`, 시드 20261020, sqlite3)
   - `users` 2,000명: 테스트 계정 약 3%, 유입 채널 NULL 약 8%
   - `events` 방문 로그: 한 유저가 하루 1~3회 방문 (fan-out 재료)
   - `orders`: 방문한 날에만 주문이 생기고, 주문 시각은 하루 중 아무 때나
   - `channels`: 채널 이름 룩업 (NULL 채널은 없음)
   - `ref_daily`: 외부 기준 역할. SQL 마트와 따로 파이썬으로 원천 행을 세어 만든 9월 일별 주문 수와 매출
2. **마트 네 개를 두 버전으로** (`marts.py`). 집계 기간은 2026년 9월. 버그 하나가 어느 검사에 걸리는지 분명하게 보이도록 마트마다 버그를 나눠 심었다.

   | 마트 | 심은 버그 | 버그 쿼리 | 고친 쿼리 |
   |---|---|---|---|
   | 주문 마트 | 조인 fan-out으로 매출 중복 | 같은 날 방문 로그와 `JOIN` | `EXISTS`로 방문 여부만 표시 |
   | 채널별 매출 | NULL 누락 | 채널 룩업과 `INNER JOIN` | `COALESCE(channel, '미분류')` |
   | 일별 매출 | 기간 경계(포함/미포함) | `order_ts BETWEEN '2026-09-01' AND '2026-09-30'` | `>= '2026-09-01' AND < '2026-10-01'` |
   | 전환율 KPI | 분모 모집단 불일치 | 분모 = 전체 가입자 수 | 분모 = 9월 방문한 비테스트 유저 수 |
   | 전환율 KPI | 정수 나눗셈 | `buyers / visitors` | `1.0 * buyers / visitors` |

   타임스탬프가 문자열 `'2026-09-30 14:00:00'`이면 `'2026-09-30'`보다 커서 `BETWEEN`의 끝에서 빠진다. 그래서 9/30은 00:00 이후 주문이 전부 사라진다.

3. **검사 함수** (`checks.py`). 모두 `{table, check, level, passed, detail}`을 돌려준다.

   | 검사 | 확인하는 것 | 비교 대상 |
   |---|---|---|
   | 행 수 보존 | 마트 행 수 = 원천 행 수 | 원천 `orders` |
   | 키 유일성 | 키 조합 중복 0개 | 마트 자신 |
   | 합계 대조 | 마트 합계 = 기준 합계 | 원천 `orders`, 외부 기준 `ref_daily` |
   | 분모 정의 확인 | 마트 분모 = 지표 정의서의 모집단 수, 분자 <= 분모 | 원천 `events`, `users` |
   | 비율 계산 확인 | 저장된 비율 = 같은 행의 분자 / 분모 (실수) | 마트 자신 |
   | 경계 확인 | 날짜가 9/1~9/30을 빠짐없이, 넘치지 않게 덮음 | 기대 달력 |
   | 전수 대조 | 모든 날짜, 모든 컬럼이 셀 단위로 같음 | 외부 기준 `ref_daily` |

4. **레벨 매기기** (`suite.py`). 빌드가 돌면 V0에서 시작해, V1 검사가 전부 통과하면 V1, V2 검사까지 전부 통과하면 V2, V3 검사까지 통과하면 V3. 문서 전체 레벨은 가장 낮은 마트를 따른다.

## 결과

![검사 결과 행렬](outputs/check_matrix.png)

**원고의 검증 레벨과 이 키트 검사의 대응**

| 레벨 | 원고의 정의 | 이 키트에서 해당하는 것 | 잡는 버그 |
|---|---|---|---|
| V0 미검증 | 쿼리가 돌아갔다 | `build_marts`가 에러 없이 끝남 | 없음 (버그 마트도 통과) |
| V1 자기 일관성 | 자동 검사(합계, 키 유일성 등) 통과 | 키 유일성, 비율 계산 확인, 경계 확인 | fan-out(키 중복), 정수 나눗셈, 기간 경계 |
| V2 외부 부분 대조 | 내가 만들지 않은 기준과 일부 기간이나 일부 컬럼을 맞춤 | 행 수 보존, 합계 대조, 분모 정의 확인 (원천 로그, 외부 기준과 합계 한 숫자씩) | fan-out(행 수, 금액), NULL 누락, 기간 경계, 분모 모집단 불일치 |
| V3 외부 전수 대조 | 외부 기준과 전 기간, 전 컬럼을 셀 단위로 맞춤 | 전수 대조 (일별 매출 30일 x 2컬럼 = 60셀) | 기간 경계 (9/30 행 불일치) |

원고의 자동 검사 패턴 6가지 중 합계 등식(합계 대조), 키 유일성, 분모 NULL/0(비율 계산 확인에서 분모가 0이나 NULL이면 실패), 기간 누락(경계 확인)은 위 검사로 들어갔고, 퍼널 단조성과 0행 적재는 이 데모의 버그와 맞지 않아 다루지 않았다.

읽을 것은 두 가지다.

- **키 유일성은 NULL 누락과 기간 경계를 못 잡는다.** 행이 빠지는 버그는 남은 행끼리는 멀쩡하기 때문이다. 마트 안만 보는 V1 검사로는 "없는 행"을 알 수 없고, 원천이나 외부 기준과 맞춰 봐야(V2) 드러난다
- **버그 마트의 레벨은 V0**다(채널별 매출만 V1). 빌드가 성공했다고 "검증했다"고 말하면 이 마트가 그대로 공유된다

**고친 마트의 검증 카드** (`outputs/validation_card.md`, run.py가 생성)

```
[검증 카드]  레벨: V2   대상: 고친 마트 4개

- 마트별 레벨 : 주문 마트 V2, 채널별 매출 V2, 일별 매출 V3, 전환율 KPI V2
- 문서 레벨   : 가장 낮은 마트를 따라 V2
- 대조 기준   : 원천 orders, events, users 테이블 / 외부 기준 ref_daily (9월 일별 주문 수, 매출)
- 결과        : 검사 11개 중 11개 통과
- 미검증      : 채널별 매출과 전환율은 합계, 분모 한 숫자만 외부와 맞춤(채널 단위 셀 대조 안 함). 9월 이외 기간. 지표 정의 자체가 맞는지는 검사 범위 밖
- 재현 방법   : python run.py
- 검증자      : 자동 검사
```

일별 매출은 V3이지만 다른 마트가 V2라서 문서 전체는 V2다. 원고의 "체인의 강도는 가장 약한 고리로 정해진다"를 그대로 따른다.

## 한계와 다음 단계

- **검사를 전부 통과해도 정의가 맞다는 뜻은 아니다.** 분모 정의 확인은 "정의서와 같은가"만 본다. 정의서가 분모를 처음부터 잘못 잡았다면(예: 방문자가 아니라 가입자) 검사는 통과한다
- 이 데모의 외부 기준 `ref_daily`는 같은 원천을 파이썬으로 따로 센 것이다. 실무에서는 운영 대시보드 원본, 다른 팀 산출물, 재무 확정치처럼 정말로 내가 만들지 않은 기준이어야 V2, V3로 인정된다. 내가 만든 재현 쿼리와 맞춘 것은 최대 V1이다
- 버그를 마트마다 하나씩 나눠 심었다. 실무에서는 버그가 겹쳐 서로 상쇄될 수 있다(예: fan-out으로 늘고 경계 오류로 줄어 합계가 우연히 맞음). 그래서 합계 하나보다 행 수, 키, 셀 단위 대조를 함께 돌리는 편이 안전하다
- 검사는 원천 테이블이 아니라 실제로 소비하는 마트에 돌렸다. 원천에 돌리면 테스트 계정처럼 원래 걸러질 행 때문에 과탐이 난다
- 다음 단계: 퍼널 단조성, 0행 적재 검사 추가, 채널 단위 셀 대조로 채널별 매출을 V3로 올리기, 검사 결과를 실행마다 기록해 "불일치를 몇 번 찾았나" 이력 남기기

## 실행

```
pip install -r ../requirements.txt
python run.py
python -m pytest tests
```

run.py는 `data/mart_buggy.sqlite`, `data/mart_fixed.sqlite`(원천 테이블 + 마트), `outputs/` 아래 그림 1개, 결과 표, 검증 카드를 만든다(약 8초). tests는 작은 표본(유저 400명)으로 "버그 마트는 해당 검사 실패, 고친 마트는 전부 통과"와 검사 함수별 알려진 정답을 확인한다.
