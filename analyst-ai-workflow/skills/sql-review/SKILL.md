# SQL 리뷰

목적: 쿼리가 "돌아가는지"가 아니라 "맞는 숫자를 내는지"를 먼저 본다. 리뷰를 받은 사람이 다음 쿼리에서 같은 실수를 하지 않게 원인까지 적는다.

## 먼저 읽을 것
- `references/rubric.md`: 항목별 배점과 감점 기준
- `references/example-review.md`: 리뷰 한 건의 완성 예시. 출력 모양을 여기에 맞춘다

## 절차

### 1. 문제의 grain부터 적는다
쿼리를 읽기 전에 문제 문장만 보고 한 줄로 적는다.
- 결과 한 행은 무엇인가 (예: 가입 월 하나)
- 분모 모집단은 누구인가 (예: 그 달 가입자 전원, 구매자만이 아님)
- 기간 조건은 어디에 걸리는가 (모집단 정의인가, 측정 창인가)

이 세 줄과 답안이 다르면 그것이 가장 큰 감점 사유다.

### 2. 작은 데이터로 실제로 돌린다
- 문제에 맞는 표본 데이터를 sqlite3 메모리 DB에 만든다. 엣지 케이스를 일부러 넣는다: 구매가 0건인 사용자, 같은 날 2건 구매, 기간 경계에 걸린 행, NULL
- 손으로 계산한 기대값과 답안 결과를 비교한다
- 결과가 다르면 어느 행에서 갈라지는지 찾는다. 추측으로 "틀렸다"고 쓰지 않는다

### 3. 오류를 두 갈래로 나눈다
- **수치가 달라지는 오류**: 조인 후 행 복제(fan-out), 분모 모집단 오류, 정수 나눗셈, WHERE와 HAVING 위치, 날짜 경계 포함 여부. 단호하게 쓴다. 무엇이 어떻게 달라지는지 숫자로 보인다
- **실행만 막는 오류**: 함수 이름 오타, 쉼표 누락, 방언 차이. 체크리스트로 가볍게 모은다

### 4. 효율과 자연스러움
- 같은 테이블을 여러 번 읽는지, 필요 없는 정렬이나 DISTINCT가 있는지
- CTE는 하나의 역할만 맡고 이름이 역할을 말하는지 (`first_orders`, `monthly_signups`). `cte1`, `final_result` 같은 이름은 감점
- 실무에서 잘 안 쓰는 함수나 과하게 압축한 한 줄 쿼리는 감점. 다음 사람이 고칠 수 있는 쿼리가 좋은 쿼리다

### 5. 출력
아래 순서를 지킨다.
1. 점수표 (rubric.md 네 항목)
2. 수치가 달라지는 오류 (각각: 무엇이, 왜, 어떻게 고치나)
3. 실행 오류 체크리스트
4. 잘한 점
5. 모범 답안: 주석은 what이 아니라 why를 적는다
6. 실무 연결: 이 실수가 대시보드나 보고서에서 어떤 잘못된 결론을 만드는지 한두 줄

## 하지 말 것
- 돌려 보지 않고 결과가 틀렸다고 단정하기
- 답안 원문을 고쳐서 인용하기. 원문은 그대로 두고 고친 버전을 따로 보인다
- 모범 답안을 지나치게 압축하기. 리뷰 대상보다 읽기 어려운 모범 답안은 쓸모가 없다
